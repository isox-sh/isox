## Development setup

Use Node.js 24 or 26+ for repository development. Vitest 5 excludes Node.js 25;
the CLI, core, and JS executor support Node.js 24+.
The repository uses pnpm workspaces, with packages under `packages/`. Install
[pnpm](https://pnpm.io/installation) using the version pinned in `package.json`,
then run `pnpm install` from the repository root. Commit changes to
`pnpm-lock.yaml` alongside dependency updates; use `pnpm install --frozen-lockfile`
in CI.

Builds use TypeScript 7 (`tsc`), installed as `@typescript/native`. The
`typescript` dependency aliases Microsoft's TypeScript 6 compatibility package
for ESLint's compiler API requirements. This follows the
[TypeScript 7 migration guidance](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/#running-side-by-side-with-typescript-6-0).

```bash
pnpm install
pnpm bootstrap # Builds core, the executors, and CLI from a clean checkout
pnpm isox run-many --target=lint # Runs every project's lint target
pnpm isox run-many --target=lint --fix # Automatically fixes supported lint issues
pnpm isox run-many --target=test # Runs every project's test target
pnpm isox test e2e # Runs only the end-to-end suite
```

## Tests

Package tests live in their owning package's `tests/` directory. Repository-wide
action, bootstrap, and packaging tests live in the root `tests/` directory and run
with `pnpm isox test workspace`. After bootstrapping,
`pnpm isox run-many --target=test` runs every project's test target, including the
package suites, workspace tooling tests, end-to-end suite, and website validation. Use
`pnpm isox test <project>` to run one suite, such as `pnpm isox test cli`.
Rebuild changed packages before running their tests.

The Vitest end-to-end suite lives in `e2e/` and runs with `pnpm isox test e2e`
after bootstrap. It uses the public [`@isox-sh/e2e`](/docs/plugin-testing)
helper. Each test creates a workspace under `<root>/tmp/isox-e2e-*`, links the locally built
CLI/core/JS packages, and runs the CLI as a child process. It creates `isox.json`
using `isox init`, initializes a JS project with `--importPath`, builds it, checks
JavaScript and declaration outputs, executes the compiled code, and verifies a
rebuild after editing source. Relative and absolute project paths are covered.
The root `tmp/` directory is excluded from Git, lint, and Isox project discovery.
Fixtures are removed after each test, including failures. These tests require no
registry access and exercise local builds; they do not test published tarballs.

## Continuous integration

Pull requests and merge groups run the `pull-requests` workflow using `.github/actions/setup-isox` to set up
Node.js and pnpm, install dependencies, and build core, the CLI, and the
plugins. Call this action once after checkout in each job that needs Isox; subsequent steps in that job can
use `pnpm isox`. It defaults to Node.js 24, configurable through `node-version`.
The planning job creates an affected matrix for `test`, `build`, and `lint` through
our `actions/plan` action. Each target gets up to three workers, which bootstrap
their prerequisites and use `actions/run-many` to execute the exact planned
projects. The website's `test` target validates Mintlify alongside the package
and end-to-end tests. Projects' `plan.weight` values balance expensive commands.
Changes propagate through inferred and declared dependencies; workspace-wide
inputs select all projects with the requested targets. Unowned paths are ignored
unless matched by `affected.globalFiles`; `affected.ignoreFiles` excludes matching
files before selection.
A final required check preserves failures and accepts an empty plan. Pull requests
use their base SHA; other events use the nearest reachable Git tag, or all
projects if none exists. This workflow runs only for pull requests and merge groups.
See [affected projects and CI](/docs/affected-and-ci) for the public actions.

```yaml
steps:
  - uses: actions/checkout@v7
  - uses: ./.github/actions/setup-isox
  - run: pnpm isox lint core
```

## Building and running packages

Packages have Isox `project.json` files with `build`, `lint`, and `test` commands.
Run `pnpm bootstrap` once to bootstrap the local CLI, then use Isox itself:

```bash
pnpm isox build core
pnpm isox build js
pnpm isox build cli
pnpm isox build vitest
pnpm isox lint core
pnpm isox lint cli
pnpm isox test core
pnpm isox test cli
pnpm isox test js
pnpm isox test vitest
pnpm isox test nx
```

The syntax is `isox <command> <project>`: `build` is the target, and `cli` is the project.
Any command defined in that project's `targets` object can be used.
`isox run cli:build` also works. `init`, `add`, `run`, `reset`, `affected`, `plan`,
and `run-many` are reserved CLI commands; use `isox run <project>:<command>` for
project commands with those names.

Package builds use [`@isox-sh/js:tsc`](/docs/typescript), written as `js:tsc`
in our project files. Compiler settings stay in each package's `tsconfig.build.json`;
there are no `scripts.build` entries. Lint commands use
[`eslint:lint`](/docs/eslint); test commands use
[`vitest:test`](/docs/vitest).
The root `tsconfig.json` covers all package sources with `noEmit: true`. Editors
use this workspace config without a package-level `rootDir` boundary. Internal
package imports use the root `tsconfig.base.json` paths, which point to the
original sources in `packages/*/src`. Package build configs keep `rootDir: "./src"`
so emitted files stay directly under `dist/<package>`. The `js:tsc` executor creates
a temporary build config that maps dependencies to their compiled declarations. Build
prerequisites first; editor navigation and workspace discovery use the source
aliases without needing a build. Root development
dependencies keep the local plugins available to Node and the CLI; TypeScript
paths do not rewrite emitted imports. Source package manifests omit internal
`@isox-sh/*` dependencies, and package generation restores the dependencies needed
by their published code and types. Workspace discovery infers project edges, so
package project definitions do not duplicate these imports.

Isox uses `dependencies` for affected selection but does not schedule prerequisite builds yet: build core before JS
and the other packages when rebuilding manually. `pnpm bootstrap` seeds core and the JS executor
with TypeScript, then runs the package build commands through Isox. It also
refreshes discovery. After editing a `project.json`, use `pnpm isox reset` to
refresh discovery on the next run.

## Build outputs

All repository packages build into `<repository>/dist/<package>`, including
`dist/core`, `dist/js`, `dist/eslint`, `dist/vitest`, `dist/nx`, `dist/e2e`,
`dist/semver`, and `dist/cli`. These directories contain runnable package artifacts: JavaScript,
declarations, rewritten package manifests, executor manifests, and schemas.
Source files and tests stay under `packages/<package>`.

Each package's `tsconfig.build.json` declares the root output path. Its Isox build
enables `generatePackageJson`, and executor schemas are copied using `assets`. Generated
manifests use paths within the output package and resolve workspace dependency
versions. `publishConfig.directory` selects this output for packaging; pnpm's
`linkDirectory` makes local workspace imports resolve to it after installation.
Run `pnpm install` after changing these settings, then `pnpm bootstrap` before
running the CLI or tests. Publish or globally install the built package directory
when using npm directly. See [trying the local CLI](#trying-the-local-cli) for the
global installation commands.

Bootstrap seeds the metadata and schemas needed to compile core and JS, prepares
shared dependency links under `dist/node_modules`, then rebuilds every package
through Isox. The TypeScript executor tracks ownership of bootstrap metadata so
it can safely replace it during the build. Bootstrap refreshes outdated dependency
links and the workspace discovery cache while retaining output ownership, so
subsequent builds can remove outputs from deleted source files. Build directories
are ignored by Git.

## Plugin source layout

Keep executors in `src/executors/<name>/<name>.executor.ts` and their options
schemas beside them as `<name>.schema.json`. Put project initializers in
`src/generators` and reusable helpers in `src/helpers`. Tests belong to the
package's `tests` directory.

In `packages/<plugin>/executors.json`, reference the compiled implementation and
copied schema under `../../dist/<plugin>/executors/<name>/`. Add executor schemas
to the build's `assets` option and enable `generatePackageJson`. Package generation
copies the manifest and rewrites its paths relative to the output package.
Publish `dist/<plugin>` using `publishConfig.directory`, as described in
[build outputs](#build-outputs). See [plugin layout and packaging](/docs/custom-executors#plugin-layout)
for an alternative layout with a package-local `dist` directory.

## Trying the local CLI

After installing dependencies with `pnpm install`, run these commands from the
Isox repository root to build your checkout and install its CLI globally:

```bash
node ./scripts/bootstrap.cjs
npm install -g ./dist/cli --install-links=false
```

The global `isox` command links to this checkout's built CLI.
[`--install-links=false`](https://docs.npmjs.com/cli/v12/commands/npm-install/#install-links)
keeps the local package linked. After changing source code, rerun
`node ./scripts/bootstrap.cjs` from the repository root to update the build used
by the global command. Executor plugins still resolve from the workspace where
you run Isox. A workspace-installed core also takes precedence over the CLI's
copy, so testing a local CLI alone does not replace that workspace's plugins.

Use it from a workspace containing `isox.json`, `project.json` files, and installed
executor plugins:

```bash
cd /path/to/your/workspace
isox build my-app
```

You can also invoke the built CLI directly:

```bash
cd /path/to/your/workspace
node /path/to/isox/dist/cli/index.js build my-app
```

## Documentation

The Mintlify site lives in `website/`, with navigation and branding in
`website/docs.json`, the homepage in `website/index.mdx`, and guides in `website/docs/`.
Preview it from the repository root:

```sh
pnpm isox serve website
```

The preview normally runs at `http://localhost:3000`. Before submitting docs
changes, run `pnpm isox test website` to validate the build and internal links,
including heading anchors. These commands live in `website/project.json` and use
Mintlify through `pnpm dlx`, downloading its tooling on first use. Validation uses
a pinned CLI version.
Run `pnpm bootstrap` once after installing repository dependencies to prepare the
local Isox CLI.

Add new pages to `navigation.groups` in `website/docs.json` using paths such as
`docs/getting-started`. Include a `title` and
`description` in each page's YAML frontmatter, use extensionless site paths such
as `/docs/configuration` for internal links, and keep code examples consistent with
the source and schemas. Existing Markdown guides and new MDX pages are both
supported. Use GitHub URLs for source files outside `website/`. The website's
`test` target is selected automatically by the existing affected CI plan and runs
in the shared worker. Mintlify handles hosting from this directory.

See the [documentation README](https://github.com/isox-sh/isox/blob/main/website/README.md)
for direct CLI commands and Mintlify hosting setup.

## Pull requests

Create a branch, make a focused change, and run the affected build, lint, and test
targets. For documentation changes, run `pnpm isox test website`.

Use a Conventional Commit message, such as `fix(core): Handle missing configurations`.
Use the owning project name as the scope. The
[release plugin](/docs/semver#how-versions-are-calculated) uses commit types and
breaking-change markers to determine versions.

Open a pull request describing the behavior changed and the checks you ran.
Include screenshots when a change affects the website's layout.
